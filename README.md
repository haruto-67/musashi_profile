# ドラマー個人ページ

あるドラマーの個人ページ。GitHub Pages で公開する前提の静的サイト。
このファイルは「なぜこの形になったか」を残すためのもの。新しく作業を始めるときはここから読む。

---

## 1. 何のためのページか

- 対象は個人のドラマー。複数バンドに正規メンバーとして在籍しつつ、サポートでも臨時参加している。
- 目的は **経歴を見せること**。集客用の公式サイトではない。
- **検索には引っかからなくていい**（むしろ引っかからない方がいい）。名刺やDMからURLを直接踏んでもらう想定。
  - `<meta name="robots" content="noindex, nofollow">` と `robots.txt` で除外している。
  - ただしこれは「見つかりにくくする」だけで、URLを知っている人は誰でも見られる。報酬額など出したくない情報を載せる場合はそこを理解した上で。

## 2. 載せるもの（確定した構成）

上から順に：

1. **ヘッダー** — 全幅の写真＋名前
2. **自己紹介** — 短い文章
3. **条件** — 活動地域 / 機材
4. **条件（つづき）** — 日程について / 報酬について
5. **SNS・連絡先** — X / Instagram / YouTube / Mail
6. **BANDS** — 在籍バンド一覧。それぞれ紹介文とSNSリンク、写真
7. **SUPPORT** — サポートで入ったバンドの一覧（年＋内容）
8. **SCHEDULE** — これから3ヶ月のライブカレンダー
9. **フッター** — ひとこと＋noindexの注記

順番は BANDS → SUPPORT → SCHEDULE で確定。

※ 当初案では「条件（強調）」に活動地域・報酬、「条件（補足）」に日程・機材を置く想定だったが、実装では活動地域／機材、日程について／報酬について、の組み合わせになっている。実装優先で上記に修正。**さらに2026-09-07、本人の希望で「強調・補足」の見た目の区別自体を廃止し、4項目とも同じスタイルに統一した**（`docs/style.css` の `.info`。旧 `.info.sub` は削除）。SNSも当初はTikTokを含める想定だったが、実装ではX / Instagram / YouTubeの3つのみ。

## 3. デザインの経緯

最初にA〜Fの6方向を試して、**Aのセットリスト／リソグラフ風**が採用に。そこからA1〜A4の刷り色違いを検討。

並行して、本人の写真（深夜の路上、街灯のアンバーとティールの夜空、奥にドラムセット）を渡されて、その色と空気に寄せた案（streetlight）を作成。

最終形は **その2つのハイブリッド**：

- **ヘッダーと配色は streetlight から** — 全幅の写真、右上の街灯グロー、下へ夜色に溶けるグラデーション
- **それ以外の構成はA系から** — 刷り物っぽいノイズ、大きなバンド名タイポ、正方形のバンド写真、2カラムのSUPPORT、罫線のあるカレンダー

### 途中で変えた仕様

- 写真セクションを作る → **やめた**。写真はヘッダー・ポートレート・バンドごと・帯として本文に仕込む形に。
- カレンダーを3ヶ月ぶん縦に並べる → **やめた**。長すぎたので1つにして月切り替えボタンに。
- フッターに連絡先 → **やめた**。上部に移動。フッターはひとことと注記だけ。

## 4. ファイル構成

**公開ルートは `docs/` 配下。** リポジトリ直下ではない点に注意（`89297b3 公開用にsrcからdocsへ` で移行済み）。

```
.
├── README.md
└── docs/                    GitHub Pages の公開ルート（Settings → Pages → Source は main ブランチの /docs）
    ├── index.html           本文。テキストの書き換えはほぼここだけで済む
    ├── style.css            全スタイル。色は先頭の :root にまとまっている
    ├── gigs.js              ライブ予定のデータ（ここを更新するのが日常運用）
    ├── calendar.js          gigs.js からカレンダーと一覧を組み立てる
    ├── robots.txt           検索エンジン除外
    ├── CNAME                カスタムドメイン（www.musashi-drums.com）
    ├── .nojekyll            Jekyll処理を無効化するための空ファイル
    └── images/              写真を置く
```

### images/ に入れるファイル（現状すでに実写真が入っている）

| ファイル名 | 使われる場所 |
|---|---|
| `hero.jpg` | ヘッダー全幅 |
| `portrait.jpg` | 自己紹介の右 |
| `band-Emp+ee.jpg` | バンド「Emp+ee」 |
| `band-Reliance.jpg` | バンド「Reliance」 |
| `live-wide.jpg` | BANDSとSUPPORTの間の帯 |
| `favicon.png` | `<link rel="icon">` で参照 |

ファイルが無い場合は下敷きの色で塗られるだけなので、揃うまで放置してよい。
バンド写真・ポートレート・帯写真は CSS 側で自動的にアンバー×ティールのデュオトーンになる。ヘッダーだけは元の色のまま出す。

参照先は `index.html` の `style="--src:url('images/xxx.jpg')"` で指定している。

> `docs/favicon.jpg`（`images/` 直下ではなく `docs/` 直下）はどこからも参照されていない未使用ファイル。アイコン追加時の作業ファイルが残った可能性がある。実害はないが、整理するなら削除して問題ない。

## 5. ライブ予定の更新

`gigs.js` の `GIGS` 配列に1行足すだけ。カレンダーは **今月から3ヶ月ぶん** を自動で表示するので、過ぎた月は勝手に消える。

```js
{d:"2026-09-05",     // 日付 YYYY-MM-DD
 b:"バンド1",         // バンド名（カレンダーのマス・一覧の両方にこのまま出る）
 e:"深夜の三角形 vol.4",// ライブ名
 c:"下北沢",           // 地名
 v:"ERA",             // 会場名
 o:"18:30",           // OPEN
 st:"20:10",          // 出番
 n:"3マン"}           // 備考バッジ。不要なら ""
```

- カレンダーのマスには `e`（ライブ名）と `b`（バンド名）がそのまま出る。**短縮名フィールドは無い。**
- **この2段組（ライブ名の下に小さくバンド名）はスマホ幅でも同じ。** 一時期スマホでは `.ev u{display:none}` でライブ名を隠していたが、下の一覧・PC表示と食い違うため元に戻した（2026-09-09）。
- マスの中では**折り返した上で、ライブ名・バンド名それぞれ2行まで**出し、それ以上は `-webkit-line-clamp` で「…」に丸める（2026-09-09）。長い名前でもマスの高さが揃うようにするため。全文は `title` 属性に入れてあるのでPCならホバーで読める。
- **マスをタップすると、下の一覧の該当行までスクロールして一瞬光る**（2026-09-09）。そのため `.ev` は `<span>` ではなく `<button>`、一覧の各行には `id="gig-<その月の中での連番>"` を振ってある。連番は月を切り替えるたびに振り直される。
- `e` が空のうちは、マスには代わりに `n`（「詳細未解禁」など）が出る。`n` も空なら「予定あり」。**空のマスだとタップ先が分からなくなるため。** 一覧側の見た目は従来どおりで変えていない。
- 下の一覧には 日付・曜日 / `e` + `b`（`n`があれば併記） / `c` `v` / OPEN と出番が出る。
- **一覧では、未入力の項目は「-」で埋まる**（2026-09-09）。空のままだと行によって桁がずれ、見る側には意味の分からない余白になっていたため。対象は `e` `b` `c` `v` `o` `st` の6つで、`n`（備考バッジ）は無いときは出さないまま。`c` と `v` は隣り合わせなので、両方空のときだけ「-」を1つにまとめている。
- 同じ日に複数入れると、そのマスに積まれる。

## 6. 公開手順（GitHub Pages）

1. `docs/` フォルダ一式をリポジトリに push
2. Settings → Pages → Source を `main` ブランチの **`/docs`** に設定（ルートではない）
3. カスタムドメインを使う場合は `docs/CNAME` にドメイン名を1行で置き、DNS側にもそのドメインのCNAMEレコードを設定する。**現状は `www.musashi-drums.com` を設定済み**
4. `https://www.musashi-drums.com/` で見られる

`docs/.nojekyll` によりJekyllのビルド処理を無効化している（ファイル名にアンダースコア始まりのディレクトリ等があっても無視されないように）。ビルド不要の素のHTML/CSS/JSなので、それ以外の設定は要らない。

## 7. 公開前にやること（現状の進捗）

- [x] 名前・タイトルを実名に差し替え済み（長谷川武蔵 / MUSASHI HASEGAWA）
- [x] ヘッダー・ポートレート・バンド写真・帯写真を実写真に差し替え済み
- [x] favicon を設定済み
- [ ] バンド紹介文が `説明-------` のプレースホルダーのまま（Emp+ee / Reliance とも）
- [ ] SNSリンクの `href="#"` が未設定（プロフィール欄・各バンドリンクとも）
- [ ] 連絡先メールアドレスが `musashi@example.com` のダミーのまま
- [ ] SUPPORT実績が「バンド1」〜「バンド10」のプレースホルダーのまま
- [ ] `gigs.js` のバンド名が「バンド1」〜「バンド7」のプレースホルダーのまま（日付・会場・ライブ名等は実データらしき内容）
- [ ] 活動地域・機材・日程について・報酬についての文章は実装済みだが、内容（特に「基本無償」の記述）をこのまま公開してよいか本人確認が必要

## 8. 検討の余地があるところ

- ヘッダーが画面の高さいっぱい（`min-height:86vh`。モバイルは`72vh`）。スクロールしないと何のページか分からないので、さらに下げる選択肢もある
- カレンダーは3ヶ月固定。増やすなら `calendar.js` の `m<3` を変える
- ライブが増えてきたら `gigs.js` が長くなる。JSONに切り出して fetch する形にもできるが、下記の追記（本人が更新できる仕組み）で `content.json` に統合される予定なのでここでは手を入れない
- バンド名が長いとカレンダーのマス表示が崩れうる（5節参照）。短縮名フィールドは実装しないと決定済みなので、対応するなら表示側のCSS（折り返し・省略）で吸収する

## A. なにを解決したいのか

ドラマー本人が、自分でページの内容を更新したい。ただし本人はwebに詳しくない。

したがって最優先の要件は **「どこを編集したらどこが変わるか」が一対一で分かること**。
機能の豊富さや自動化の度合いより、この一点を優先する。

### 検討して却下した案（同じ道を戻らないように）

| 案 | 却下した理由 |
|---|---|
| Googleスプレッドシート直編集 | スマホで9列を横スクロールしながら編集するのが現実的でない |
| Googleフォーム | 「送信したら何かが増える」形式は一対一の対応が見えない。修正・削除ができない |
| Notion / GitHub Issues を入力元にする | 本人がそのサービスを覚える必要がある |
| TimeTreeから定期取得 | iCal書き出しは廃止、APIも2023年12月終了。`timetree-exporter` は非公式でメール＋パスワードが必要。一度きりの移行用であって常設の自動化には向かない |
| 共有Googleカレンダー | 有力だったが、「別アプリの画面」である点で下記のエディタ案に劣る |
| Googleドキュメント（文章系）/ ドライブ（画像） | 同上。ただし将来の代替案としては生きている |
| Cloudflare Workers を中継に使う | 完全無料で組みたいという方針から除外 |
| Raspberry Pi を中継に使う | 公開リポジトリからPiへの攻撃経路を作りたくない |
| 鍵にPiのIP・ポートを混ぜて隠す | 隠蔽は防御にならず、鍵が漏れたときに所在まで同時に漏れる。鍵が長くなり運用も壊れる |

### 採用する案

**ページと同じ見た目の編集画面を `/editor` に用意して、その場で書き換える。**

「見えているものを直接いじる」以上に分かりやすいものはない、というのが選定理由。
入力欄の隣にリアルタイムプレビューを置くことで、一対一の要件を完全に満たす。

## B. 全体構成

```
[エディタ /editor]  ブラウザで編集、パスワードでHMAC署名
        │  POST（本文にJSON文字列）
        ▼
[Apps Script ウェブアプリ]  署名検証・リプレイ対策・レート制限
        │  repository_dispatch（GitHubトークンはここにだけ存在）
        ▼
[GitHub Actions]  docs/content.json を書き出してコミット
        │
        ▼
[GitHub Pages]  再デプロイ。docs/index.html と docs/editor が新しい内容を読む
```

登場するのは Pages・Apps Script・Actions の3つだけ。すべて無料枠に収まる。
ページのソースにトークンは一切出ない。エディタが持つのは「本人が毎回貼るパスワード」だけ。

### 責務分担

| コンポーネント | やること | やらないこと |
|---|---|---|
| `/editor`（静的） | 入力UI、プレビュー、署名の生成、POST | 認可の判断。GitHubへの直接アクセス |
| Apps Script | 署名検証、リプレイ・レート制限、`repository_dispatch` の発行 | データの加工・整形 |
| Actions | `docs/content.json` の書き出しとコミット | 認証（Apps Scriptを通過した前提で動く） |
| `index.html` | `content.json` を読んで描画 | 書き込み |

## D. エディタ `/editor` の要件

### D-0. 入り口のパスワードゲート

**パスワードを通すまで、編集画面を描画しない。**

1. 開いた直後はパスワード入力欄だけを表示する
2. 入力されたら、タイムスタンプに署名して Apps Script の `auth` に投げる
3. 200 が返ったら編集画面を描画する。401 ならエラーを表示して留まる

検証ロジックは `publish` と同じものを使い回す（F節）。

目的は2つ。エディタのUIを不特定の人に見せないことと、**パスワードの総当たりを防ぐこと**。
後者のためにサーバー側で検証する必要がある。クライアント側でハッシュを比較する方式だと、ソースを読んでオフラインで総当たりできてしまう。

**限界も理解しておくこと。** `docs/editor/index.html` のソース自体は誰でも読めるので、ファイルの存在は隠せない。隠せるのは操作だけ。
なお、**確定前の編集内容はブラウザの中だけに存在し、どこにも送信されない。** 下書きが外部から見えることはない。

### D-1. 基本方針：ページそのものを編集する

**別画面のフォームではなく、ページと同じ見た目のまま、各要素を直接書き換える形にする。**

- `docs/editor/index.html` として配置し、`https://www.musashi-drums.com/editor/` で開く
- `style.css` を本体と共用する（`docs/style.css` を参照）。レイアウト・配色・書体はページと完全に同じ
- 起動時に `content.json` を読んで、現在の内容がそのまま並んだ状態で表示する
- 各テキストが入力欄になっていて、打った内容がその場に反映される

この形にすると、別途プレビュー領域を持つ必要がない。**編集画面がそのままプレビューになる。**
「どこを編集したらどこが変わるか」という本要件の中核は、この一点で満たす。

### D-2. 文章部分

**文章はすべてテキストボックスにする。** 表示専用の箇所を残さない。対象は以下のすべて。

**例外：ヘッダー（`profile.role` / `profile.name` / `profile.nameEn` / `profile.heroImage`）は編集対象に含めない。** 名前・肩書き・ヘッダー写真は「そもそも変更することがない」項目なので、エディタでは表示のみ（クリックしても変更できない）。実装後に本人からのフィードバックで確定した仕様。

| 場所 | キー | 入力欄 |
|---|---|---|
| 自己紹介 | `profile.lede` | 複数行 |
| 活動地域 | `profile.area` | 複数行 |
| 機材 | `profile.gear` | 複数行 |
| 日程について | `profile.schedulePolicy` | 複数行 |
| 報酬について | `profile.fee` | 複数行 |
| フッターのひとこと | `profile.word` | 複数行 |
| 連絡先 | `profile.email` | 1行 |

- 複数行の欄は**内容に合わせて高さが自動で伸びる**こと。スクロールバーの中で書かせない
- 空にしたときは、その項目ごと非表示になる（見出しだけ残さない）
- 入力欄と分かる程度の枠線は出すが、フォントサイズや行間は表示時と同じにする。打った文字がそのままの見た目で並ぶこと

### D-3. 画像

**写真をクリック（タップ）すると変更・追加できる。**

- 対象は ポートレート `portraitImage` / 帯 `stripImage` / 各バンドの `image`。**ヘッダー写真（`heroImage`）は対象外**（上記D-2の例外と同じ理由）
- 写真の上にカーソルを乗せる、またはフォーカスすると「変更」のオーバーレイが出る。押すとファイル選択が開く
- まだ画像が無い枠は、下敷きの色に「＋ 写真を追加」と表示しておく
- 選択した直後に、その場の表示が新しい画像に差し替わる（アップロード完了を待たない）
- 各画像に「削除」も用意する。削除すると空の枠に戻る
- 確定を押すまでは実際のアップロードを行わない

**ブラウザ側で必ず縮小してから送る。**

- 長辺 1600px を上限、JPEG 品質 0.82 程度、目安として 500KB 以下
- スマホの写真は数MBあるので、そのまま送ると通信も処理も詰まる
- 縮小は canvas で行う。EXIF の回転情報で向きが変わるので、`createImageBitmap` の `imageOrientation: 'from-image'` などで正しい向きに補正する（**縦写真が横向きになるのは頻出の不具合**）

**ファイル名は上書きせず、毎回新しい名前にする。**

- `images/<種別>-<UNIX秒>.jpg` の形（例 `images/hero-1757200000.jpg`）。これは `content.json` に入れる相対パスであり、アップロード先の実際のリポジトリパスは `docs/images/<種別>-<UNIX秒>.jpg` になる（F節参照）
- 同じ名前で上書きすると、ブラウザやCDNのキャッシュで古い画像が出続ける
- 使われなくなった画像は残るが、Gitの履歴にも残るので消さない（K節参照）

### D-4. SNSリンク

プロフィールのSNSと、各バンドのリンクの両方に同じUIを使う。

- 既存のリンクはそれぞれ**ボタン名の入力欄**と**URLの入力欄**が並ぶ
- 各行の右に「×」。押すと削除（確認ダイアログを出す）
- 一覧の末尾に「＋」。押すと空の行が1つ増える
- ボタン名は短い文字列（`X` `Instagram` `Bandcamp` など）、URLは `https://` で始まること。形式が違う場合はその場で赤く示す。ただし**確定はブロックしない**（本人が入力途中で詰まらないように）
- **本番ページ側では、SNSリンク（プロフィール・バンドとも）はすべて新規タブで開く**（`target="_blank" rel="noopener noreferrer"`）。ページから離脱させたくないため。実装は `docs/render.js` の `renderSns()`

### D-5. 一覧の追加・削除

参加バンド・サポート・スケジュールの3つとも、同じ操作感で揃える。

| 一覧 | 1件の中身 | 追加 | 並び |
|---|---|---|---|
| 参加バンド | 名前 / 期間 / 紹介文 / 写真 / リンク一覧 | 一覧の末尾に「＋ バンドを追加」 | 「↑」「↓」で入れ替え |
| サポート | 年 / 名前 / 内容 | 一覧の末尾に「＋ 行を追加」 | 「↑」「↓」で入れ替え |
| スケジュール | 日付 / バンド名 / ライブ名 / 地名 / 会場 / OPEN / 出番 / 備考 | 一覧の末尾に「＋ ライブを追加」 | **日付順に自動で並ぶ**（手動の並べ替えなし） |

- 削除は各件の右上の「×」。**確認ダイアログを必ず挟む**（スマホでの誤タップ対策）
- 追加した直後の空の1件に、そのままカーソルが入ること
- 並べ替えはドラッグではなく上下ボタンにする。スマホでのドラッグは誤操作が多い
- スケジュールの日付は日付入力、OPEN と出番は時刻入力を使う。スマホの標準UIが出るようにする
- **短縮名（`sh`）の入力欄は無い。** そもそも `content.json` にこのフィールドを持たないため（C節・K節参照）
- **編集中は日付を変えても並び替えない。** 一覧の並び替えロジックはD-5表の通り「日付順に自動」だが、これは**確定時に適用する**もので、編集画面上でその場で行を動かすと操作しづらい（特に新しく追加した行が編集中に勝手に移動すると困る）。新規追加した行は確定を押すまで末尾に留まる。エディタを開いた直後の初期表示は日付順のままでよい
- **スケジュールには月タブを付ける。** 全件を1本の縦長リストで出すと本人が探しづらいという指摘があり、`.calnav`（本番のカレンダーと同じ見た目）を編集欄の上にも置いた。**本番は今月から3ヶ月表示だが、編集側は今月から4ヶ月分のタブを出す**（月替わり直後に来月分が空にならないよう、常に1ヶ月分先に入力しておけるようにするため）。タブは表示フィルタのみで、データそのものは絞り込まない。日付未入力の行と、今月より過去の日付の行は、どのタブを選んでいても常に表示する（新規追加した行を見失わないため、および過去分を削除できる状態を保つため）

### D-6. 確定と状態表示

- 画面下部に固定のバーを置き、**「確定」ボタン**を配置する。**パスワード入力欄はここには置かない**——D-0の入り口で入力したパスワードを、ページを開いている間だけメモリ上に保持して使い回す（毎回貼り直させない）
- パスワードは**保存しない**。localStorage にもCookieにも書き込まない。ページを閉じる・再読み込みすると消え、次回また入り口から入力し直しになる
- 確定の処理順は、**画像のアップロード → 完了した画像のパスを入れた `content.json` の送信**
  - 画像が複数ある場合は1枚ずつ送る。進捗（3枚中2枚など）を表示する
  - 画像の送信に失敗したら、そこで中断して `content.json` は送らない
- 送信後の状態を必ず画面に出す。**成功／パスワード違い／時刻ずれ／回数制限／通信エラー**を区別して表示する
- 成功時は「反映まで1分ほどかかります」と添える
- **失敗してもフォームの入力内容を消さない**
- 未保存の変更がある状態で離脱しようとしたら警告する

## E. 署名仕様

**HMAC-SHA256 の共有秘密方式。** 公開鍵方式（ECDSA等）は採用しない。
理由は、パスワードを毎回手で貼る運用にした時点で秘密を共有しているのと同じであり、公開鍵方式にする利点が消えるため。加えて Apps Script には ECDSA の検証関数が標準で存在しない。

### ペイロード

```jsonc
{
  "ts": 1757200000,        // UNIX秒
  "content": { /* C節の content.json と同じ構造 */ },
  "sig": "hex文字列"
}
```

### 署名対象文字列の作り方（**エディタ側と検証側で必ず同じ実装を使う**）

1. `content` を「キーを再帰的に昇順ソートし、区切り文字に空白を含めない」JSON文字列に正規化する
2. `String(ts) + "." + 正規化したJSON` を署名対象とする
3. パスワードを鍵として HMAC-SHA256 を計算し、小文字hexで `sig` に入れる

> ここが実装でいちばん事故る箇所。キー順や空白が1文字ずれるだけで検証が通らない。
> **正規化関数は1つのファイルに書いて、エディタと Apps Script の両方から同じものを使うこと。**
> 実装したら、既知の入力に対する期待値をテストケースとして残す。
>
> **実装して分かった落とし穴：文字コード。** Apps Script 側で `Utilities.computeHmacSha256Signature(message, secret)` に文字列をそのまま渡すと、日本語などのマルチバイト文字を含むメッセージでブラウザ側（常にUTF-8）と結果がずれることがある。`Utilities.newBlob(message, "text/plain", "utf-8").getBytes()` で明示的にUTF-8バイト列に変換してから渡すこと（`appsscript/Code.gs` の `hmacHex` 参照）。空データ（`auth`）だけでテストすると気づけないので注意。

ブラウザ側は Web Crypto（`crypto.subtle.importKey` + `sign`）、Apps Script 側は `Utilities.computeHmacSha256Signature` を使う。

### 検証（Apps Script 側）

順に確認し、1つでも落ちたら GitHub には一切触れずに終了する。

1. `ts` が現在時刻から **±5分以内** か
2. `ts` が **スクリプトプロパティに保存した「最後に受理した ts」より大きい** か（リプレイ対策）
3. `sig` が一致するか（**タイミング安全な比較**を使う。単純な `===` は避ける）
4. レート制限内か（**1時間あたり20回**を上限とする）

検証を通過したら、`ts` を「最後に受理した ts」として保存してから先へ進む。

## F. Apps Script の要件

### デプロイ設定

- 実行するユーザー：**自分（オーナー）**
- アクセスできるユーザー：**全員**

URLを知っていれば誰でもPOSTできる状態になるが、E節の検証が最初の関門として機能する。

### CORS（**ここを外すと動かない**）

Apps Script のウェブアプリはプリフライトに応答しない。したがって**単純リクエストの条件を満たす形でしか呼べない**。

- リクエストの `Content-Type` は **`text/plain;charset=utf-8`**（JSONは文字列化して本文に入れる）
- **カスタムヘッダを一切付けない。** 署名もタイムスタンプもすべてボディの中に入れる
- `mode: 'no-cors'` は**使わない**。使うとレスポンスが読めず、成否を本人に伝えられなくなる
- レスポンスは `ContentService.createTextOutput(JSON.stringify(...)).setMimeType(ContentService.MimeType.JSON)`

### つまずきやすい点

- `/exec` は302を返して `script.googleusercontent.com` へ飛ぶ。fetch は自動で追うが、**「全員がアクセス可」になっていないとログイン画面のHTMLが返り、JSONパースで落ちる**。エラー内容がCORSと無関係になるため原因を見失いやすい
- **コードを変更したら新しいバージョンとしてデプロイし直さないと反映されない。** 「直したのに動かない」の大半がこれ。URLを固定したい場合は既存デプロイの編集で新バージョンを指定する

### 受け付けるアクション

ボディの `action` で2種類を切り分ける。**どちらも E節の署名検証を通過しないと処理しない。**

| action | 用途 | 経路 |
|---|---|---|
| `auth` | エディタの入り口の認証（D-0） | GitHubには触れず 200/401 を返すだけ |
| `uploadImage` | 画像1枚の保存 | GitHub Contents API に直接 PUT |
| `publish` | `content.json` の更新 | `repository_dispatch` |

画像を `repository_dispatch` に載せないのは、`client_payload` の上限が 64KB で画像が入りきらないため。
`uploadImage` は `{path, base64}` を受け取り、Contents API（`PUT /repos/<owner>/<repo>/contents/<path>`）でコミットして、保存されたパスを返す。**`path` はリポジトリ内の実パスであり `docs/images/...` で渡ってくる／検証する**（`content.json` に保存する相対パス `images/...` とは別物なので混同しないこと）。

- `path` は `docs/images/` 配下のみ許可する。**`..` やそれ以外のディレクトリを弾く**
- 拡張子は `.jpg` `.png` `.webp` のみ
- 1枚あたり 2MB を上限とし、超えたらエラーを返す

### レート制限

`publish` は1時間あたり20回、`uploadImage` は1時間あたり30回を上限として、それぞれ別に数える。

`auth` は**失敗した回数だけを数え、1時間あたり10回を超えたらその間すべて拒否する**。
成功したリクエストはカウントしない。ここは緩めないこと。

> **成功も含めて数えてはいけない。** `auth` は認証前なので呼び出し元を識別できず、カウンタが全体で1つになる。
> 成功も数える設計にすると、攻撃者が1時間に10回投げるだけで枠を使い切り、**本人が正しいパスワードを入れても弾かれる**。
> 失敗だけ数える方式なら、正しいパスワードを持っている本人はいつでも通る。打ち間違えた直後に打ち直しても問題ない。

なお `auth` はリプレイ判定（E節の2番）の対象外にする。認証は何度も繰り返すものなので、`LAST_TS` を更新すると正規の操作が弾かれる。

### GitHubへの通知（publish）

検証通過後、`repository_dispatch` を POST する。

```
POST https://api.github.com/repos/<owner>/<repo>/dispatches
{ "event_type": "content-update", "client_payload": { "content": { ... } } }
```

`client_payload` の上限は 64KB。現在のデータ量なら問題ないが、超えた場合に備えて **サイズ超過時は明示的にエラーを返す**（黙って切り捨てない）。

### スクリプトプロパティに入れるもの

| キー | 中身 |
|---|---|
| `HMAC_SECRET` | 本人に渡すパスワード |
| `GITHUB_TOKEN` | fine-grained PAT |
| `GITHUB_REPO` | `owner/repo` |
| `LAST_TS` | 最後に受理したタイムスタンプ |
| `RATE_LOG` | レート制限用の記録（`publish` / `uploadImage` の実行回数、`auth` の**失敗**回数） |

**コードにベタ書きしない。** プロジェクトを誰かと共有した瞬間に漏れる。

## G. GitHub Actions の要件

- `on: repository_dispatch` で `types: [content-update]`
- `permissions: contents: write`
- `client_payload.content` を **`docs/content.json`** として書き出す
- **書き出す前にスキーマを検証する。** 必須キーの欠落や型の不一致があれば失敗させ、壊れたJSONをコミットしない
- **差分がなければコミットしない**（空コミットを積まない）
- **`docs/CNAME` と `docs/.nojekyll` は対象に含めない。** 書き込み処理は `docs/content.json` 単体のみを対象にし、`docs/` を丸ごと同期・削除するような実装にしない（カスタムドメイン設定が消えるとPagesの配信ごと壊れる）
- コミットメッセージは `content: update via editor (<updatedAt>)` のような形で、由来が分かるようにする
- 失敗した場合に気づけるよう、Actions の通知を有効にしておく

## H. セキュリティと運用

### GitHubトークン

- **fine-grained PAT** を使う。対象リポジトリは1つ、権限は **Contents: write のみ**
- 期限は最長1年。**切れると無言で動かなくなる**ため、期限日をカレンダーに登録しておく
  （この構成でいちばんありがちな「半年後に突然使えなくなる」がこれ）

### パスワードが漏れたとき

1. Apps Script のスクリプトプロパティの `HMAC_SECRET` を新しい値に変える
2. 本人に新しいパスワードを渡す

これだけで即座に無効化できる。エンドポイントのURLはページにハードコードされているが、URLだけでは何もできない。

### 運用の取り決め（決定済み）

- **パスワードの受け渡しはLINE。** 本人がトークを遡れば見つかるので、紛失の心配はしない前提
- 紛失・漏洩した場合は、にわとりさんが `HMAC_SECRET` を変えて新しいものをLINEで再送する
- **誤操作からの復旧は、にわとりさんがGitの履歴から戻す。** エディタに「元に戻す」は入れない
- 編集するのは本人ひとり。バンドメンバー等が触ることはないので、**鍵は1本のみ**

### 壊れたときの挙動

- Apps Script が落ちていても、**ページ自体は静的なので無事**。編集ができなくなるだけ
- `content.json` の取得に失敗した場合、ページは空白にせず、直前の内容またはビルド時に埋め込んだ既定値を表示する
- どうにもならないときは、にわとりさんがリポジトリの `docs/content.json` を直接編集すれば復旧できる。**詰みの状態が存在しない**ようにしておくこと

## I. 実装の順序（推奨）

- [x] 1. `docs/content.json` を作り、`docs/index.html` がそれを読んで描画するよう改修（`gigs.js` を統合・削除。`calendar.js` の描画ロジック自体は変更不要——引き続き `b` をそのまま表示する）
- [x] 2. `docs/editor` を作る（`docs/editor/index.html` + `editor.js` + `editor.css`）。ページと同じ見た目で直接編集する形（D-1）にしたため、別途プレビュー領域は無い
- [x] 3. 正規化＋HMAC生成を実装（`docs/render.js` の `canonicalize`/`canonicalJSON`、`editor.js` の `signPayload`）。Apps Script と同じロジックのモックサーバーを立てて Playwright で自動テストし、一致を確認済み
- [x] 4. `appsscript/Code.gs` を実装し、実際に Apps Script へデプロイ済み（`clasp` を使用。デプロイ自体は Apps Script API 経由だと「アクセスできるユーザー：全員」が反映されないことがあり、最終的に Web UI の「新しいデプロイ」で作り直した）
- [x] 5. `repository_dispatch` を受ける `.github/workflows/content-update.yml` と検証スクリプト `.github/scripts/validate-and-write.js` を実装。実際に `publish` を1回実行し、Actions が `docs/content.json` のみ書き出して `docs/CNAME` / `docs/.nojekyll` に触れないことを確認済み
- [x] 6. 画像のアップロード（縮小・向き補正・`uploadImage`。保存先は `docs/images/`）を実装。実際にテスト画像を1枚アップロードして GitHub 上に反映されることを確認後、削除して後片付け済み
- [x] 7. 通しで動作確認済み。**この過程で実機特有のバグを1件発見・修正した**（下記参照）

### 実機テストで見つかったバグ

- **HMAC計算の文字コード不一致。** `auth`（空データ）の署名検証は最初から通ったが、日本語を含む `publish` の署名だけが `bad_signature` になった。原因は `Utilities.computeHmacSha256Signature(message, secret)` に文字列をそのまま渡すと、マルチバイト文字の扱いがブラウザ側（常にUTF-8）と食い違うことがあるため。`appsscript/Code.gs` の `hmacHex` で `Utilities.newBlob(message, "text/plain", "utf-8").getBytes()` を使って明示的にUTF-8バイト列に変換してから渡すよう修正して解決した。**E節の正規化と合わせて、Apps Script側でHMACを組む際は必ずこの形にすること。**
- **contenteditableのEnterキー。** 複数行のテキスト欄（`profile.lede`/`area`/`gear`/`schedulePolicy`/`fee`/`word`、バンド紹介文）で改行すると、ブラウザが素の `"\n"` ではなく新しい `<div>` を挿入する。`document.execCommand('insertText', false, '\n')` で回避しようとしても、Chromeは内部でこれも改段落として扱ってしまい効果がない（実機検証で確認済み）。対処は諦めて回避せず、**読み出し側で正規化する**方式にした：`editor.js` の `getPlainText()` が `<div>`/`<br>` を `"\n"` に変換してから `content.json` に書き出す。見た目側の副作用（`<div>` がCSSのアクセント枠線を拾って謎の線が増える）は、次の項目のCSS修正で別途解消した
- **CSSの子孫セレクタが編集時に生成される要素を拾う。** `.info div{...}`（活動地域・機材・日程・報酬のブロック装飾）が子孫セレクタだったため、上記のEnterで生成された `<div>` にもアクセント色の枠線が付いてしまっていた。`.info>div` に直して直接の子だけに限定して解消
- **CSS Gridの子要素がトラック幅を押し広げてスマホで横スクロールする。** `.intro`（自己紹介まわり）・`.band`（バンド情報）のグリッドで、子要素にmin-widthの指定が無いと、中の文字列の「最小コンテンツ幅」がグリッドトラックを本来の幅より広げてしまい、スマホ幅で横スクロールが発生していた。`.intro>*{min-width:0}` / `.band>*{min-width:0}` を追加して解消。**グリッド内のテキスト量が変わりうる箇所（＝ユーザーが自由に書ける入力欄）を新しく作るときは、この`min-width:0`を忘れると同じ不具合が起きるので注意。**
